# Initiating the API schema linter

[Story selector](../story-bank.md) · [Culture framing](../culture-framing.md) · [Gaps](../gaps.md)

**Use for:** Initiative, finding an unassigned problem and turning standards into useful tooling. Another episode within S01.

**Research questions:** Q07; partial support for Q14. **State:** Draft ready for rehearsal. No independent rehearsal recorded.

## Opening

> I noticed that adopting schemas would not make API designs consistent, so I initiated a linter based on our architect’s guidelines.

## Answer structure

1. **Gap:** APIs could all have schemas and still be structured inconsistently.
2. **Initiative:** Researched tools, found inspiration in Google’s public API linter and began between PR reviews and at a hackathon.
3. **Alignment:** Connected the proposal to architecture’s direction and agreed with my manager to plan tasks, timelines and repository introduction.
4. **Result:** Built the linter; architecture valued its contribution to standardization.

## Frame for the question

Lead with the gap you independently identified. Explain why automation was useful, then how you coordinated introduction. Manager approval is supporting context.

**Culture connection:** People Over Process can connect to taking responsibility for an unassigned problem. Explain what useful work the rules supported; automated process is not automatically good process. See the [memo-based framing guide](../culture-framing.md) for the source and interpretation.

## Spoken draft

> During our schema-first initiative, I noticed that our APIs were structured inconsistently. Giving every API a schema would still leave that design inconsistency. Architecture was introducing written API guidelines, and I saw an opportunity to turn them into automated checks.

> I found inspiration in Google's public API linter and started working on our own tool between PR review cycles and during a hackathon. I then discussed introducing it with my manager, connecting the proposal to the broader standardization effort. We agreed to plan the tasks, timelines and how to introduce it to our repositories.

> I built the linter using the architect's guidelines. The architecture team valued how it helped standardize our APIs. The idea and initial work came from me, and I involved my manager in planning its introduction.

## Keep the claims precise

- Credit the architect for the standards.
- Do not imply a fully specified rollout, company-wide compliance, or a tradeoff against another priority that you have not described.

## Follow-up preparation

- What did you include first, and why? For a prioritization question, what competing work did you actually defer?
