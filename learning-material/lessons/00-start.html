Netflix L5 live coding preparation in Go

A 14 hour course for reasoning through unfamiliar coding problems, explaining decisions to another senior engineer, and adapting when requirements change.

This course assumes basic programming experience and focuses on your first technical interview through CodeSignal. It does not assume a particular Netflix team or a guaranteed question list. Your original plan gives caches and rate limiting extra weight; this course adds enough algorithms to avoid preparing for only one kind of problem. Recommendation exercises are small programs with explicit contracts, rather than an ML system design syllabus.

How to spend the 14 hours

The estimates include reading or listening, thinking aloud, implementing, testing, and reviewing. Reading every page without doing the exercises will take much less time and will not provide the same preparation. Use each lesson's time box. Stop when it expires, record what was difficult, and revisit that skill later. Optional extensions are outside the 14 hour route.

The interview loop to practise

First restate the observable behavior. “For each user, I need to accept at most three requests in the preceding ten seconds, excluding the left boundary.” Ask about ambiguous inputs that change the algorithm: sorted arrival, duplicate IDs, concurrency, capacity, and return values. Avoid spending ten minutes collecting hypothetical requirements.

Next give a correct baseline. A scan can be a useful first version. Identify its expensive operation, then select a structure that makes that operation cheaper. Say the invariant before writing the implementation. An invariant is a claim that is true before and after every public operation: for example, every live cache key has exactly one node in both the map and the recency list.

Walk one tiny example manually. Implement a vertical slice that runs. Test the example, an empty input, an exact boundary, and a case that defeats your first idea. Explain time and space using meaningful variables. “Each request is appended once and removed once” is stronger reasoning than merely saying “linear.” Finish with the next requirement and what would actually change.

A suggested 50 minute rehearsal budget is five minutes to clarify and model, five to discuss the baseline and improvement, twenty five to implement, ten to test, and five for a follow-up. This is a practice schedule, not a claim about Netflix's interview duration. If your invitation gives another duration, scale it. In a live session, tell the interviewer when you need a minute to think and return with a concrete hypothesis.

Think aloud. A prompt says, “Build a cache.” Name three questions that change the representation and one question you can defer. Explain why each matters.
Coach notes

Capacity policy, expiration policy, and required operations or concurrency can change the design. Whether values are strings or movie metadata often does not change the first design. A good answer connects each question to a decision, rather than reciting a requirements checklist.

Reading and listening

Start with the lesson, then code in a blank file. The quick-start guide explains the file layout. After an attempt, inspect the runnable references: algorithms.go, cache.go, and services.go. Their corresponding test files contain boundary cases and comparisons against simpler models. These are learning examples, with assumptions and limitations documented in the code.

Every concept has prose that can stand without the code. Listen pauses at “Think aloud” checkpoints. Speak your answer before pressing Continue; reveal the coach notes afterward if needed. Code blocks are for the later hands-on part and are skipped by narration. Browser speech uses the voices available on your machine; voice quality and offline availability depend on the voice.

For an actual conversation, copy the AI tutor prompt for the current lesson into an AI tool that supports voice. It supplies the lesson and tells the tutor to ask one question at a time, challenge your assumptions, and withhold solutions until you have tried. The local reader has narration and reflection checkpoints; it has no embedded AI service or microphone recording.

Your first 30 minutes

Spend ten minutes with this orientation, ten explaining a map based duplicate detector without code, and ten writing it in Go. Return the first repeated ID and a boolean. Test an empty list, two adjacent duplicates, a duplicate far apart, and no duplicate. If syntax blocks you, spend extra time in lesson 1. If the code is easy but explaining why it works is hard, keep every later speaking checkpoint.
