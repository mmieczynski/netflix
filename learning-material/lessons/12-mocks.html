Live mocks and a readiness rubric

Test whether you can derive and explain a solution under time pressure, including a change you did not prepare verbatim.

How to run the two mocks

Each mock is forty five minutes followed by ten minutes of review, totaling one hundred ten minutes. Use a blank Go file and a minimal environment. Have a partner or AI reveal only the candidate brief first. Keep hints and interviewer notes closed. During a mock the coach should answer clarification questions but should not teach unless you explicitly request a hint. These are original practice prompts, not reported Netflix questions.

Mock one candidate brief

Build an in-memory cache for video metadata. Expose Put(key, value, ttl) and Get(key), with a maximum entry count. Successful reads and writes mark entries most recently used. Get must never return expired data. Use an injected clock. Values can be strings. Talk through behavior and complexity before coding; implement a correct running baseline before optimizing cleanup.

Clarify the zero-capacity behavior, exact expiry boundary, nonpositive lifetime, overwrite behavior, and when expired entries are physically removed. Your first version can use straightforward cleanup if you explain its cost. Show tests using a fake clock.

Think aloud. Before opening notes or coding, state your proposed contract, the structures you would use, and the invariants that connect them. Then set a forty five minute timer.
Mock one interviewer script and follow-ups

At about minute five, accept these defaults if the candidate asks: zero capacity stores nothing; expiration occurs exactly at the deadline; nonpositive TTL removes the key; overwrite resets TTL; expired entries should be removed before evicting a live item on Put. Start single-threaded.

At about minute twenty five, ask: “Get should avoid scanning the whole cache. Expired entries that are never read should eventually be reclaimed.” Let the candidate choose cleanup scheduling and acknowledge its latency. At about minute thirty five, ask: “An entry is overwritten before its old expiry. Could cleanup delete the new value?” If the implementation is ahead, add concurrency and ask which Get operations mutate state.

Useful test trace: capacity two, clock zero, put A with TTL five and B with TTL twenty; get A; advance to five; put C with TTL twenty. A is expired and removed; B and C remain. At time six overwrite C with TTL fifty; cleaning at its earlier deadline twenty five must retain the new C.

Strong reasoning separates recency and deadline order, keeps map/list state consistent, and avoids pretending full cleanup is constant time. A correct map scan plus honest complexity and a clear upgrade path is better preparation than a heap implementation the candidate cannot explain.

Mock one reference architecture

Store map key to node, a doubly linked list, and optionally deadline heap records with generations. Get checks its node's deadline and removes or promotes it. Put drains expirations if required by capacity semantics, updates or inserts, then evicts from the list tail. All removals update the map and list once. Under lazy heap invalidation, stale records are permitted but cannot delete a mismatched generation. A single mutex can protect each complete operation when concurrency is added. The supplied LRU and TTL building blocks demonstrate the pieces; combining them is the mock.

Mock two candidate brief

You receive a finite list of viewing events, each containing event ID, user ID, title ID, positive watch duration, and integer timestamp. At a supplied now, return the k titles with greatest total watch duration during the last W ticks. The interval excludes now minus W and includes now. Duplicate event IDs represent redelivery and should count once. Tied totals rank by ascending title ID. Explain assumptions about duplicates and input ordering.

Begin with a batch query so a full scan is allowed. Return IDs and totals. Preserve the input. Invalid nonpositive durations can be rejected or skipped if you state the policy and use it consistently. Do not assume the events are sorted unless clarified.

Think aloud. What must be deduplicated, what must be aggregated, and what must be ranked? Which state would you retain if this later became a stream?
Mock two interviewer script and follow-ups

Clarify that identical event IDs have identical payloads in the first version. Events outside the query window are ignored; now and W share units. Default k nonpositive to empty. A correct baseline filters, deduplicates IDs, aggregates by title, then sorts.

At about minute twenty five, ask for top k selection when the unique title count is large and k is small. At about minute thirty five, change to monotone streaming events with repeated queries at nondecreasing now. Ask how old contributions are removed and whether a heap of only k winners remains sufficient as totals decrease.

Test at now ten, W five: e1 on A at time six duration three, e2 on A at time nine duration four, duplicate e2 again, e3 on B at time ten duration seven, and e4 on C at time five duration one hundred. A and B each total seven; A ranks first; C is excluded by the left boundary. Add a future event at eleven and ensure it does not enter the batch answer.

Strong follow-ups retain per-event contributions for expiration, discuss deduplication retention separately from the ranking window, and recognize that score decreases can require reconsidering candidates outside the winner heap. A simple aggregate map with sorting on query is a valid streaming baseline with explicit query cost.

Mock two reference reasoning

Let n be events and u distinct in-window titles. Batch scan plus deduplication and aggregation takes expected O(n), followed by O(u log u) sorting, or O(u log k) bounded heap selection and O(k log k) output ordering. Space includes up to O(n) event IDs and O(u) aggregates. Streaming uses a chronological queue with exact contributions to subtract and a map of sums; remove titles whose live count reaches zero. A deduplication horizon shorter than the possible redelivery delay can allow repeat counting. If late events are accepted, the queue assumption changes.

A coaching rubric rather than a company scorecard

Score each area from zero to two: zero means missing, one means partly correct or prompted, two means independent and clear. This is an original study rubric, not Netflix's hiring rubric. Score contract clarity, data structure rationale, invariant and correctness reasoning, runnable Go implementation, boundary testing, and response to the follow-up. The maximum is twelve.

Use the score to select practice, not predict an offer. A zero in correctness or runnable implementation needs attention even if the total is high. If explanation is weak, rerun a familiar problem while speaking without reading your old code. If a new follow-up causes a rewrite, practise identifying exactly which invariant changed and which helpers can remain.

The error log that makes repetition useful

After each mock record: the mistaken assumption, the smallest counterexample, the invariant that would prevent it, and a different problem that uses the same idea. Example: “I deleted a refreshed key with its old timer. Counterexample: overwrite before expiry. Fix: only a matching generation may delete. Transfer: rescheduled jobs.” Revisit after two or three days from a blank file.

Do not repeat the exact same input until your fingers know it. Change one condition: negative values, duplicate timestamps, out-of-order arrival, weighted capacity, missing keys, score decreases, or concurrent callers. If the algorithm stops working, articulate why before fixing it. This is the distinction between recalling code and learning an approach.

Before the interview

Use the CodeSignal environment associated with your invitation. Check the Go version, function-versus-program template, how tests are run, and how output is displayed. Practise one tiny map exercise there so interface uncertainty is separate from problem difficulty. Confirm the session's allowed resources from its instructions. The platform supports different workflows, so do not assume automated-assessment timing applies to your live interview. CodeSignal practice guidance.

On the day, use short reasoning statements: “This operation changes recency, so it needs the write lock.” “The predicate is false before the insertion point and true after it.” “That memory bound omitted stale records; the correct bound includes them.” Calmly correcting a claim is part of clear engineering communication.
