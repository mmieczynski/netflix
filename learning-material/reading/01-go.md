# Chapter 1 — Go and data structure choices

Choose a structure by the operations you need to make cheap. The story around the data is secondary.

## From requirements to representation

Imagine a list of recently watched movies. If you only append and iterate, a slice is a natural fit. If you repeatedly ask whether a particular movie has been watched, add a set. If you must remove the least recently accessed movie while promoting arbitrary movies on access, a slice alone makes each promotion expensive. A map plus a doubly linked list answers both identity and recency questions.

A slice gives constant time indexed access and amortized constant time append. Amortized means a sequence of appends has linear total work even though an individual append may allocate and copy the entire backing array. Inserting or deleting in the middle generally shifts elements and costs linear time. A map gives expected constant time lookup, insertion, and deletion; it does not preserve order. Include key hashing cost when keys themselves are long strings.

A stack removes the newest item. Use it for unfinished nested work, depth first traversal, and undo. A queue removes the oldest item. Use it for breadth first traversal or chronological expiration when arrival and expiration order agree. A heap exposes the smallest or largest priority cheaply but does not keep every element globally sorted. A balanced search tree supports ordered updates and predecessor queries; a sorted slice gives simpler binary search when updates can be appended or are infrequent. Go's standard library does not provide a general ordered map.

| Need | First candidate | What it does not solve | 
| --- | --- | --- |
| Membership or key lookup | Map or set | Sorted order, oldest item | 
| Process in arrival order | Queue with head index | Out of order deadlines | 
| Next minimum repeatedly | Min heap | Arbitrary key lookup without an index | 
| Most recent and least recent | Doubly linked list plus map | Earliest expiration | 
| Latest version before a time | Sorted slice per key | Cheap arbitrary historical insertion | 
| Connections and dependencies | Adjacency list | Implicit cycle protection | 
| Prefix lookup | Trie, or sorted strings plus search | Low memory automatically | 

For listening: identity suggests a map; arrival order suggests a queue; smallest priority suggests a heap; arbitrary recency changes suggest a map and linked list. These are starting hypotheses. The contract and workload decide whether they are appropriate.

## Go mechanics that prevent interview bugs

Initialize a map before assigning into it. Reading a missing key yields the value type's zero value, so use the second boolean result when zero is a valid stored value. A set is often a map from keys to empty structs. Map iteration order is unspecified; sort extracted keys when the result must be deterministic. These rules are documented in the [Go specification](https://go.dev/ref/spec#Map_types).

```go
seen := make(map[string]struct{})
seen["movie-1"] = struct{}{}
_, exists := seen["movie-1"]
delete(seen, "movie-1")
_ = exists

queue := []int{0}
for head := 0; head < len(queue); head++ {
    node := queue[head]
    _ = node // append newly discovered nodes here
}
```

A slice is a view over an array. Copying the slice value does not copy the elements; an in-place sort can change the caller's data. Use an explicit copy when your contract promises preservation. Reslicing a long-lived queue may retain its backing array. Clear pointer slots when discarding values and occasionally compact or use a ring buffer for bounded services. A short interview traversal with integer IDs rarely needs elaborate memory reclamation.

A string is bytes. Indexing returns a byte; ranging decodes runes, and the range index is a byte offset. If the task defines characters as Unicode code points, convert to a rune slice or maintain rune positions carefully. A rune still is not necessarily a human-perceived character: combining marks and emoji sequences can contain multiple runes. Clarify the required unit. ASCII-only tasks can use byte arrays for speed and simplicity. [Go strings, bytes, runes and characters](https://go.dev/blog/strings).

Use explicit integer widths where constraints demand them. Durations and timestamps in our exercises use integer ticks, and sums that could exceed 32 bits use int64. Ask whether multiplication can overflow. Avoid sentinel values such as minus one if they are legitimate data; return a value and a boolean. Return an error for invalid input when the prompt expects validation, rather than inventing a successful result.

**Failure case.** A map from movie ID to a single duration cannot preserve the order of individual watch events.

A single value per movie loses event multiplicity and ordering unless the value itself stores a history. Totals need accumulation; the last ten events need chronological records. The correct key is determined by the query, not merely by an available ID.

## Complexity is a budget explanation

Let n be events, u distinct users, and k returned results. Say which one your bound uses. A map of queues can hold up to u times a per-user limit, not merely the limit. Sorting n records is typically O(n log n); scanning every user's queue for one request adds work proportional to all users. Space includes maps, queued stale entries, recursion depth, and output. Distinguish auxiliary space from output space.

To justify an optimization, identify repeated work. If every lookup scans all records, an index removes that repeated scan. If every iteration sorts everything just to find the next minimum, a heap maintains enough ordering. If every recursive branch recomputes the same remaining problem, memoization reuses answers. Understanding the saved work is more durable than memorizing names.

## A slower explanation of what a data structure buys you

Think of a data structure as a decision about what work to do now so that later questions become easier. An unsorted slice is easy to build: put each item at the end. You have not organized it by identity or priority, so a later search may inspect every item. A map does more bookkeeping on insertion so that a later lookup can usually jump directly to a small part of the stored data. A sorted slice pays for order so that searches can eliminate whole ranges. None is universally best because they invest work in different capabilities.

A hash map does not magically know where every key lives. A hash function converts a key into a value used to locate storage. Different keys can lead to the same candidate location; this is a collision. The map must still compare keys or use another collision-handling scheme. That is why expected constant-time lookup is not the same as a promise that every input takes one machine instruction. You usually do not implement the hash table during an interview, but you should understand the guarantee you are relying on.

An index also has a maintenance cost. Suppose you keep a slice of movies and a map from movie ID to its slice position. Looking up a movie becomes easy. Now remove the first movie by shifting every later movie one place left. Every shifted position in the index has become wrong. The combined structure must maintain agreement between its two views. This small example foreshadows the central challenge of LRU caches: a fast structure is only useful while its invariants remain true.

Ownership is another part of representation. If two parts of a program hold slices over the same backing array, they share the elements even though each slice has its own length and capacity. Imagine handing someone a window onto a bookshelf, rather than photocopies of the books. Moving the window does not copy books; changing a visible book changes what another overlapping window sees. Appending may allocate a new shelf, so whether changes remain shared can depend on capacity. Correct code should not rely on accidental allocation behavior to provide isolation.

## Worked example: one event stream, three different questions

Suppose a viewer produces three events: A for four minutes, B for seven minutes, then A for two minutes. Before choosing a container, write down the answer the caller needs. The same input supports several incompatible summaries.

![Three representations of the same viewing events. Only the history retains both order and individual durations.](figures/representations.svg)

For total watch time by title, accumulate into a map: A becomes six and B becomes seven. For whether a title has ever appeared, keep only membership: A and B. For the last two events, keep ordered records: B for seven, followed by A for two. All three representations are correct for their own queries. Only the history can answer all three afterward, but it costs more space and may require more work per query.

| Representation | Stored state | Information discarded |
| --- | --- | --- |
| Membership set | A, B | Counts, durations, order |
| Totals map | A: 6, B: 7 | Individual events and order |
| Event history | A:4, B:7, A:2 | Nothing from these records |

This is a useful way to evaluate a proposed optimization. A smaller representation is a claim that some information will never be needed again. If the interviewer changes the query to the last two events, the totals map cannot be repaired by a clever loop. The missing history must be retained from the start or recovered from another source.

## Worked example: deletion changes the cost of an index

A slice stores movie records in the order A, B, C. A second map stores A at index zero, B at one, and C at two. Lookup is now fast, but deleting B exposes a design choice.

If display order must be preserved, shift C left and update C's map position to one. For a longer slice, every shifted record needs its index repaired. Lookup became cheaper by making updates more expensive. If order is irrelevant, replace B with the last record C and shorten the slice. Only C's index changes. Both versions remove B from the map.

The distinction matters in Go because a slice position is not stable identity. A record's index can change even when its movie ID does not. An index map therefore needs an explicit invariant: for every resident ID, the indexed slice position contains that same ID. A test that only looks up A can pass while C's stale index remains broken.

The general lesson is to choose a representation for a workload, not for one isolated operation. A directory with frequent lookups and rare deletions may justify the extra index. A three-record list queried once may be simpler to scan. Both decisions follow from how much repeated work is actually saved.

## Putting the program together: an event registry

Suppose we want to accept event IDs while preserving the order in which distinct IDs first appeared. The public operation Accept takes an ID and returns whether this call introduced a new ID. History returns the unique IDs in first-appearance order. The empty string is a valid ID. Repeated arrivals do not move an ID to the end.

The registry needs two fields: a membership set and an ordered slice. The set answers whether an ID already exists; the slice preserves an order that the set cannot supply. In Go terms, a struct could contain a map from string to empty struct and a slice of strings. A constructor initializes the map. Every ID in the slice must occur exactly once in the set, and the two structures must have equal sizes.

Accept first looks up the ID. If present, it returns false without mutation. Otherwise it records the ID in the set, appends it to the slice, and returns true. History returns the slice's contents. If callers are allowed to mutate their returned slice, History should return a copy; otherwise a caller could overwrite the registry's internal ordering without updating its set.

On A, B, A, the first two calls return true and the third false. History remains A, B. An empty input history is an empty result, not an error. A test using an empty-string ID catches implementations that confuse a legitimate value with a missing-key sentinel. A test that mutates a returned history catches accidental shared ownership.

Accept is expected constant time, with amortized append cost. Returning a protected snapshot costs linear time in the number of distinct IDs. If the next requirement is Remove, deleting from the set is easy but preserving slice order requires finding and shifting the ID. That new operation changes the workload and may justify another representation.
